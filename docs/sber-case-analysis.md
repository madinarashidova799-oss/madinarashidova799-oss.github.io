# Кейс «Разделение счёта · Сбер»: анализ и дерево метрик

Источник: тестовое задание Сбера (UX/Product Designer Test), материалы в `~/Desktop/Сбер ТЗ/`.
Статус: концепция, на пользователях не проверялась. Ожидаемое влияние ниже — гипотезы, не результаты.

## Задание
Компания друзей заканчивает ужин, один оплачивает счёт картой за всех. Нужно спроектировать разделение суммы между друзьями с опцией списка покупок из общего чека: где живёт сервис, как делится счёт, как контролируется зачисление денег.

## Насколько кейс сильный

**Сильные стороны**
1. Покрыт полный путь двух ролей, создателя и получателя, от оплаченной операции до возврата денег. Большинство решений тестовых заданий останавливаются на экране «поделить поровну».
2. Конкурентный анализ сделан руками в Т‑Банке, Альфа‑Банке и ВТБ, с двух устройств, по 11 критериям. У каждого критерия есть вывод для решения. Это самый убедительный артефакт кейса.
3. Найден системный разрыв, который не закрывает ни один из трёх банков: после отправки запроса связь с покупкой теряется, статус сбора нигде не виден, контроль остаётся на создателе. На этом разрыве построено ключевое решение: сбор как отдельный объект со статусами.
4. Гипотеза проверяемая: есть основная метрика (доля оплат в течение суток), guardrail (ошибочные оплаты) и дизайн A/B‑теста.
5. Честность: синтетические интервью прямо названы синтетическими.

## Что поправить в макетах (Figma)
- Экран «Проверьте позиции»: 1 650 + 2 300 + 950 + 1 400 + 900 + 500 + 600 = **8 300 ₽**, а сумма операции **8 400 ₽**. Распределение потом показывает «Распределено 8 400 ₽».
- Экран «Разделить счёт · по позициям»: в списке 6 позиций на **7 350 ₽** (нет салата), а «Осталось распределить» 8 400 ₽.
- Простейший фикс: салат с томатами 1 050 ₽. Тогда сумма позиций равна 8 400 ₽. Так сделано в демке на сайте.
- Получатель: 825 (½ пасты) + 500 + 200 + 150 = 1 675 ₽ сходится, но тирамису у получателя 500 ₽ при цене 900 ₽ за позицию; стоит проверить логику доли.

## Дерево метрик

```
North Star: объём P2P‑возвратов, закрытых внутри СберБанк Онлайн
│
├─ Adoption: доля ресторанных операций (MCC 5812/5814) с созданным сбором; сборы на MAU
│    ← вход «Разделить счёт» из оплаченной операции; сумма, место и дата подставлены
│
├─ Скорость создания: медиана времени от операции до отправки; доля брошенных черновиков
│    ← распознавание чека в редактируемый черновик; массовый выбор участников; 3 режима деления
│
├─ Completion (ключевая): доля получателей, оплативших за 24 ч; доля полностью закрытых сборов; время до закрытия
│    ← расшифровка позиций у получателя; пуш ведёт сразу в запрос; оплата в одно действие
│
├─ Контроль: доля сборов без ручной сверки; напоминаний на сбор
│    ← сбор со статусами (ожидаем, оплачено, ошибка); мягкое напоминание одному участнику
│
├─ Acquisition: получатели других банков → переход → оплата по СБП → установка/регистрация
│    ← безопасная веб‑оплата; понятный канал доставки запроса
│
└─ Guardrails: ошибочные оплаты; споры на сбор; обращения в поддержку
     ← проверка «распределено = сумме операции»; «Уточнить позицию»
```

Вторичный эффект для бизнеса: платить за всю компанию картой Сбера проще, когда возврат денег автоматизирован. Отсюда рост карточного оборота в ресторанах и комиссионного дохода (interchange).

**Как дизайн влияет на бизнес, одной фразой:** превращает неформальный долг между друзьями из переписки и заметок в объект банка со статусом. Деньги возвращаются быстрее и внутри экосистемы, а каждый запрос приводит в банк людей, которые ещё не его клиенты.

## Следующие шаги проверки
1. Problem‑интервью на 12–15 людях: правда ли непонятная сумма задерживает перевод.
2. Юзабилити‑тест прототипа на парах «создатель + плательщик»: может ли получатель объяснить свою сумму и заметить ошибку.
3. A/B в пилоте: запрос с расшифровкой против запроса только с суммой. Основная метрика: доля оплат за 24 ч. Guardrail: ошибочные оплаты не растут.
